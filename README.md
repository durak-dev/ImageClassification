# ImageClassification
Image classification project: data preparation (duplicate quarantine, train/val/test split, quality check + restoration), label audit with CLIP, and CNN training with Keras.

The dataset lives **inside this repository**. There is no external download.

## Data layout

```
data/
├── original/                  raw data, placed manually, never modified (committed to git)
│   ├── images/
│   └── labels.csv             filename, class_id, description (or labels/labels.csv, optionally with per-image label files)
├── split_manifest.csv         generated: which file belongs to which split (commit it so everyone shares the split)
├── train/  val/  test/        generated by the notebook (git-ignored), each with:
│   ├── images/                raw copies of the images of that split
│   ├── labels/                labels.csv, labels_corrected.csv
│   └── images_corrected/      denoised / contrast / sharpened images
utils/funcs.py                 helper functions
Preprocessing.ipynb
requirements.txt
```

If your files are still in `data/images` and `data/labels.csv`, move them to `data/original/images` and `data/original/labels.csv`.

## What the notebook does (in order)

1. **Hash** all raw images; every image with an identical twin is a duplicate and **all** its copies go to `train` (never to val/test).
2. **Split** the unique images 70/15/15 (stratified by class, two-step) **before** any preprocessing. Files are copied to `data/{split}/images` and `data/{split}/labels`.
3. **Quality check** (noise, blur, contrast) – thresholds are picked on `train` only.
4. **Restoration** reads `data/{split}/images` and writes `data/{split}/images_corrected`.
5. **CLIP label audit** on `train` + `val` (not `test`), then `labels_corrected.csv` per split.

The split is reproducible: it is stored in `data/split_manifest.csv` and reused on later runs. Delete that file only if you want a new split.

## Model notebooks (run after `Preprocessing.ipynb`)

| notebook | what it does |
|---|---|
| `MoE_comparisons.ipynb` | trains one ResNet backbone (or loads a saved one), then compares four heads on it: CNN, MoE, pMoE, MGE |
| `pMoE_MGE_finetune_v2.ipynb` | trains pMoE and MGE with several head settings on a backbone |
| `ConvNeXt_finetune.ipynb` | fine-tunes a pretrained ConvNeXt-Tiny (head first, then the whole network). Runs on Colab or on a RunPod pod; writes `ConvNeXt_finetune/models/` (weights, about 110 MB, too big for GitHub) and `ConvNeXt_finetune/results/` (run log) |

Each notebook writes its logs and weights to its own output folder, named like the notebook (`MoE_comparisons/` and `pMoE_MGE_finetune_v2/`, each with `models/` and `history_logs/`). The notebooks are independent: the only thing they can share is a **backbone file**. A backbone is saved as a complete Keras model (`<name>.keras`, layers and weights), so a notebook can load it without the code that built it. In the cell *Choose the backbone*, write the path (relative to the project folder) in `BACKBONE_PATH`, e.g. `'MoE_comparisons/models/backbone_6072k_20251118-210000.keras'`, or leave it `None` to train a new backbone, which is saved under an automatic name. The backbone is **frozen**: heads train only their own layers, so any head can be retrained without touching the backbone. The helpers are in `utils/resnet.py`. (`MoE_approach.ipynb` and `pMoE_MGE_finetune.ipynb` are the first versions of these notebooks and use the old `models/` and `history_logs/` folders.)

## Option A – Run locally (GPU or CPU)

1. Clone the repo and enter it:
   ```bash
   git clone https://github.com/durak-dev/ImageClassification.git
   cd ImageClassification
   ```
2. Create a virtual environment and activate it:
   ```bash
   python -m venv .venv
   # Windows:   .venv\Scripts\activate
   # Mac/Linux: source .venv/bin/activate
   ```
3. *(Only if you have an NVIDIA GPU)* install the CUDA build of PyTorch first, using the command for your CUDA version from <https://pytorch.org/get-started/locally/>. Otherwise skip this step; the CPU build is installed in step 4.
4. Install the dependencies:
   ```bash
   pip install -r requirements.txt
   ```
5. Make sure `data/original/` contains `images/` and `labels.csv` (it does after `git pull`).
6. Open `Preprocessing.ipynb` (Jupyter or VS Code, select the `.venv` kernel) and run the cells top to bottom.
   The "Imports and hardware" cell prints whether `cuda` or `cpu` is used.

## Option B – Run on Google Colab

1. Open Colab, then *File → Open notebook → GitHub* and enter `durak-dev/ImageClassification` (or upload `Preprocessing.ipynb`).
2. *(Optional)* *Runtime → Change runtime type → GPU* to speed up CLIP.
3. Run the cells top to bottom. The setup cell detects Colab and clones the repo into `/content/ImageClassification`. The split folders are recreated from `data/original` and `data/split_manifest.csv`, so you get exactly the same split as everyone else. Colab already has the required packages.

## Run on RunPod with local VS Code

The notebooks run in your local VS Code while the kernel runs on a RunPod GPU pod through an SSH tunnel. Run the scripts from PowerShell in the repo folder.

1. Deploy a pod with the official **RunPod PyTorch** template (Community Cloud, no network volume).
2. Copy the **"SSH over exposed TCP"** line from the pod's *Connect* tab (`ssh root@<ip> -p <port> ...`).
3. Run `.\connect_pod.ps1 -Ip <ip> -Port <port>` and wait for **READY**. Keep that window open: it is the tunnel.
4. In VS Code open a notebook, *Select Kernel* → *Existing Jupyter Server*, paste the URL (it is on the clipboard) and choose **"Python 3"**.
5. Run the notebook.
6. Run `.\pull_results.ps1 -Ip <ip> -Port <port>` to copy `checkpoints/` and the `models/` and `history_logs/` folders of each notebook from the pod into this folder.
7. **Terminate** the pod (never *Stop* it).

* The pod IP and port change with every new pod, so take them from the Connect tab each time.
* `data/` and `utils/` must be on the pod. The bootstrap handles this through git (it clones or pulls the repo from GitHub), so push your changes before you connect. Local changes you have not pushed are not on the pod.
* Results survive terminating the pod: `pull_results.ps1` copies them to your PC, and on the next pod `connect_pod.ps1` uploads the saved backbones (`<notebook folder>/models/*.keras`) and the training logs (`<notebook folder>/history_logs/*.csv`) again.
* Pick the kernel **"Python 3"** from the Existing Jupyter Server, not "Pod Python". "Pod Python" is the kernel that `setup.sh` registers and is not needed here. The Jupyter server is started with `LD_LIBRARY_PATH` cleared, so every kernel it launches (including "Python 3") sees the GPU in TensorFlow. `connect_pod.ps1` prints a warning if TensorFlow finds no GPU.

## Saving checkpoints to GitHub (Colab)

The Colab disk is wiped when the session ends. If GitHub credentials are configured, the notebook commits checkpoints (`checkpoints/df_fixed.csv`, `checkpoints/clip_results.csv`, corrected labels, split manifest) to GitHub instead of keeping them on the VM. Locally nothing is uploaded; checkpoints are plain files in `checkpoints/`.

1. Create a GitHub personal access token with write access to this repo (fine-grained token, permission *Contents: Read and write*).
2. Copy `.env.example` to `.env` and fill it in (`.env` is git-ignored – never commit it):
   ```
   GITHUB_TOKEN=<your token>
   GITHUB_REPO=durak-dev/ImageClassification
   GITHUB_BRANCH=checkpoints      # created automatically from the default branch
   ```
3. On Colab (including a Colab runtime selected as the kernel in VS Code) `.env` is not part of the clone, and the VS Code GitHub login cannot be used by code running on the VM. The notebook therefore asks for the token once per session in a hidden input box (kept in memory, never written to disk; leave it empty to skip uploading). `GITHUB_REPO` is taken from the clone's `origin`. To avoid typing it each time, add `GITHUB_TOKEN` as a Colab Secret (key icon in the sidebar, enable notebook access) or upload your `.env` to `/content/ImageClassification/`.
4. On a local kernel nothing is uploaded: checkpoints are files in `checkpoints/`, which you commit and push with the normal VS Code Git integration.

The settings are read by `utils/config.py` (environment → `.env` → Colab Secrets); the upload/download code is in `utils/github_sync.py`. Uploads go to `GITHUB_BRANCH` (default `checkpoints`), not to `main`, so they never conflict with code changes; merge or cherry-pick from there when you want them on `main`.

## Notes

* `git pull` before you start so everyone uses the same `funcs.py`, data and split manifest.
* `data/train`, `data/val` and `data/test` are generated and git-ignored; do not commit them.
* Only exact duplicates (identical file bytes) are detected. Re-encoded or resized copies of the same picture have different hashes and are not caught.
* To train on the cleaned data: `load_splits(DATA_DIR, label_file=CORRECTED_LABELS_FILE, image_folder='images_corrected')`.
